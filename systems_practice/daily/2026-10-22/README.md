# 2026-10-22 边缘端部署：请求截止时间与在途缓冲区租约

## 工业场景

机器人视觉服务接收已预处理的FP32特征，每帧17元素，两个预分配槽，单控制线程提交异步后端。业务希望10ms后不再使用陈旧结果，但设备可能仍在读输入。今天处理部署层的准入、丢弃与回收合同；不是视觉模型或GPU计算内核课。扩展容量限制为1–64槽、每槽1–1048576元素，输入payload上界为`4*capacity*elements`字节，另有容器元数据。

源码起点是[Triton core r25.08](https://github.com/triton-inference-server/core/tree/r25.08)，2026-10-22实际读`src/scheduler_utils.cc`的`PolicyQueue::Enqueue/ApplyPolicy/RejectTimeoutRequests`和头文件，并检索调度器调用端。原项目对推理排队实施超时策略，以unique_ptr移动请求；本例保留“排队失效”和“所有权转移”两个机制，独立写有界槽状态机，省略动态batch、多优先级、协议与真实backend。Triton队列判定使用`now > timeout`，本课业务合同主动选择`now >= deadline`即过期，且增加在途完成时过滤；不能把本例称为Triton实现复现。[来源记录](source.json)，上游BSD-3-Clause，未复制源码。

## 概念回顾

截止时间回答结果是否仍有业务价值，租约回答某段内存是否还被执行者使用，这两个问题必须分别建模。相机帧进入服务时已经消耗了采集与传输时间，因此应该传递同一单调时钟域的绝对截止点，不能在每级队列重新获得完整预算。墙上时钟可能被校时改变，适合日志关联，不适合直接计算本机剩余时间。例子把时间作为参数注入，用确定的边界验证代替依赖睡眠的脆弱测试。

槽位从空闲进入排队，再转为在途。排队阶段尚未交给设备，取消或过期可以直接回收；进入在途后，即使客户端断开、业务预算耗尽，设备依然可能读取输入或写入输出。此时只能标记放弃结果，等待同一提交序列上的完成证据，随后决定是否交付并回收槽位。关闭也遵守同一规则：拒绝新请求、释放排队项、排空在途项。若完成查询失败，不能把错误当作已经完成；需要进入后端故障处置流程。

可复用槽还需要区分不同代请求。仅用数组下标作为完成凭证时，迟到回调可能操作已经属于下一帧的缓冲区。例子为每次准入增加代号，完成必须同时匹配槽、代号与在途状态，重复完成和旧凭证均被拒绝。容器自动回收只保证主机对象的析构，并不自动等待设备；控制器必须先完成排空，再结束缓冲区所有者的寿命。

资源有界与低延迟也不是同一个保证。满槽拒绝阻止内存持续增长，但执行中的慢请求仍会占用容量。丢弃过期结果改善业务正确性，却不回退已经消耗的计算。采用最早截止时间选择只是一种调度策略，没有抢占能力也没有最坏执行时间证明，不能据此宣称硬实时。工程验收需要同时观察准入拒绝、排队等待、在途完成、结果年龄和回收数量，分清业务超时与实际资源释放。

## 知识图谱

```mermaid
flowchart LR
 A[单调时钟与绝对deadline] --> B[排队准入与过期清理]
 B --> C[Queued转InFlight]
 C --> D[设备完成证据]
 E[取消或关闭] --> F[在途仅标记abandoned]
 F --> D
 D --> G[核对slot和generation]
 G --> H[结果新鲜度检查]
 H --> I[Free后才允许覆盖输入]
```

前置：C++17 RAII、chrono、容器所有权。`Scheduler`只允许一个控制线程调用；跨线程回调必须先送回这个线程或另加完整同步。CPU acquire/release、CUDA event、Linux DMA同步分别解决不同层次问题，详见[ARM27](../../arm/2026-10-22/README.md)。

## 编码练习

唯一20–30分钟任务：阅读`complete`，将“取消即释放槽”的错误想法改成两阶段完成协议，并用现成测试验证。仓库交付的是完整正确版本：5分钟画状态图，10分钟在本地工作副本实现该转移，5分钟运行边界，5分钟核对取消后容量仍满、设备完成后容量恢复。不要移除代号检查或用sleep替代完成通知。

`dispatch`在最多64槽中选择最早deadline，开销O(capacity)，`submit`预分配输入后不再扩容。采用扫描便于审查；需要大量请求、多租户公平或可抢占执行时，才改为专用调度器。这里不保证EDF最优，也不测试实际网络或模型。

## 正确性验证

测试覆盖等于deadline拒绝、满槽、最早截止调度、排队过期回收、在途取消不回收、晚完成丢弃、代号过期、重复完成、设备错误、关闭拒绝与排空，最终live=0。输入采用17元素以避免只检验空对象。两个非法构造参数被拒绝；另有成功交付与空队列边界。

安全反例使用受控状态检查，不在设备读取时真的写坏内存。`device_ok=false`仅表示已确认完成但执行结果失败，不能表示同步查询失败。`complete`的`device_ok`是调用者提供的事实，本机测试只模拟它，不能证明实际CUDA/RKNN完成。生产接入应把事件观察与`complete`置于同一受控路径，SDK失败时保留租约并停止接单。

## 性能分析

今天不报告速度收益。测试中的毫秒是注入的逻辑时间，不是测得延迟。算法比较为原先“取消即回收”破坏所有权，而两阶段策略保留在途容量；这是正确性修复，不是加速。

板端验收应记录capture、enqueue、dispatch、device-complete、response五个时间戳，分别计算排队、主机调用、设备区间与结果年龄。GPU event不能测相机等待；主机SDK耗时不能叫GPU/NPU执行时间。真实负载先预热，再统计独立请求P50/P95/P99及拒绝率，至少覆盖容量1/2/8和超时突发。拒绝率上升可能换来更低完成请求延迟，必须同时报告失败请求，不能只对成功样本宣称整体改善。

本课无自写GPU kernel，因此无新增ncu/PTX/SASS热点或架构指令收益结论；GPU对照游标保持昨日Ada，下次kernel课对照Turing。CUDA13.0对Thor的sm_110命名已从[官方CUTLASS说明](https://docs.nvidia.com/cutlass/4.2.1/overview.html)核实；实际JetPack/L4T/驱动/ncu组合待板端记录，不从Orin页面推断Thor支持。

## 工程注意事项

单调时钟只在约定的域内比较，跨进程/设备时间戳须定义来源；远端绝对时间不能直接解释成本机steady_clock。close后应持续处理设备完成通知直到live=0；不能直接销毁控制器。代号溢出抛错停止复用，不能回绕。当前不支持多线程直接调用、SDK撤销、零拷贝DMA或重启恢复，迁移须验证这些接口的实际合同。

## 自测问题

两个槽均在途，一个请求刚超时且客户端已断开，另一个仍未超时；此时新帧到达、服务又收到关闭指令，设备完成事件随后以相反顺序返回。请给出每一步允许的状态转移、结果交付决定和内存回收时刻，并说明需要哪些证据。
