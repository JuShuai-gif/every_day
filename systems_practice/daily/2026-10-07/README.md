# 2026-10-07 边缘端部署：模型热更新与在途版本寿命

## 工业场景

机器人边缘推理服务更换模型时，已接收请求必须使用完整的同一版本；坏候选不能使当前服务不可用。今天聚焦部署控制面：清单验证、预热、发布与旧版本回收。输入为 `edge-v1 REV 16 GAIN`，模拟模型接收 Batch=1、16个FP32特征，输出一个FP32标量。示例不加载真实TensorRT/RKNN模型，不把小点积当设备推理；实际接入点是 `Model` 的构造、预热和析构。CPU服务需要保证无混合版本、错误可回滚、已发布旧版本有界；候选加载与SDK工作区另计内存。课程对应部署/生命周期工程能力，完整板端服务尚未验收。

## 概念回顾

模型热更新有两个不同的完成时刻：新请求开始选择新版本，以及旧版本最后一个使用者退出。发布指针只解决第一个时刻，不能据此释放旧模型。一次请求应先获取不可变快照，再用该快照读取配置、权重和执行上下文；中途重新读取全局指针会把不同版本拼在一起。共享所有权把回收条件绑定到使用者寿命，但不会自动保证对象内部可并发修改，因此示例把模型内容设为只读，并将管理端写操作串行化。

候选模型必须在可见之前完成清单解析、资源构造和预热验证。失败时销毁候选，当前快照保持原样；成功后在短临界区内检查期望版本，防止慢加载覆盖较新的发布。版本检查和发布必须属于同一提交操作，否则两个管理请求可能都基于过期状态成功。读者获取快照时使用原子共享指针接口，发布的释放语义与读取的获取语义使已完成初始化的内容可见；这不意味着接口无锁，也不替代设备执行完成事件。

旧请求可能很慢，连续发布就可能留下多份大权重。示例用弱引用跟踪一个退休版本：它仍被持有时拒绝下一次发布，从而对已发布版本施加背压。弱引用本身不延长寿命，过期检查只用于管理协议，不把裸指针借给请求。候选在锁外构造，因此总峰值仍要包含并行候选，生产实现还需限制加载并发和单候选内存。关闭服务先撤下入口，已有快照仍可完成；异步设备任务必须让完成回调持有快照，主机提交返回不是释放资源的依据。最终验收同时检查错误回滚、在途退出、版本竞争和资源边界，不能只检查一次推理输出。

## 知识图谱

```text
清单/shape合同 → 候选构造 → 预热通过 → expected revision检查 → 原子发布
                                        ↓                   ↓
                                  过期加载拒绝         请求拥有const快照
                                                            ↓
                     retired弱引用 ← 旧对象 ← 最后一个请求/设备完成释放
                            ↓
                      下一次发布背压
```

语言层是C++17的共享指针原子自由函数与对象寿命；mutex具体阻塞机制依赖标准库/OS。本例没有Linux futex、GPU事件或容器实测。配置版本、模型版本和请求trace必须一起记录，不能将ready等同于“旧版本已释放”。

## 编码练习

唯一必做任务，预计25分钟：把 `Registry::publish` 的布尔拒绝改为可区分的 `Published/Stale/RetiredBusy/Closed` 返回值，保持候选异常回滚与原有提交顺序。5分钟定位合同，12分钟修改一个接口和调用点，8分钟运行现有检查并增加四个明确返回值断言。现成版本已完整实现发布/回收机制，不要求重写线程池、模型后端或第二个量化作业。禁止把检查移出锁来缩短临界区。

## 正确性验证

Release与ASan/UBSan实际通过：空注册表、9种非法清单、预热失败保留旧版、过期期望/非递增revision、退休版本背压、两写者仅一提交、20,000次快照请求和关闭后旧租约继续执行。输入空shape拒绝，返回值以明确oracle检查；资源依赖用weak_ptr过期检查，不用use_count猜测并发状态。线程集合析构join，创建线程期间抛异常也能回收已创建线程。TSan结果见最终验证记录。

## 性能分析

本课未测推理延迟，不报告速度收益。需要上线时分别测：加载/预热耗时、发布临界区、CPU快照获取、设备kernel、队列等待、完整请求P50/P95、旧代释放时延和总驻留内存。基线“停机替换”与候选“候选预热后发布”必须接收相同请求/模型、相同并发与设备同步语义，不能以丢弃旧请求换延迟。模型很小或更新稀少时共享指针成本可能抵消收益；实时要求强时需控制销毁线程和加载并发。

## 工程注意事项

实际先读 [Triton core](https://github.com/triton-inference-server/core) 的 [model_lifecycle.cc](https://github.com/triton-inference-server/core/blob/main/src/model_repository_manager/model_lifecycle.cc)，main读取日期2026-10-07，完整commit未固定。范围：`GetModel`、`AsyncLoad`、`OnLoadComplete/OnLoadFinal`、`ModelDeleter`；BSD-3-Clause文件头。原场景是多版本推理后端加载/卸载，返回shared_ptr、后台加载、拒绝过期操作和最后引用销毁。这里是受启发的独立实现，不复制Triton代码；保留候选提交与租约机制，简化为单模型、单退休代、同步小CPU负载。Triton另线程销毁的设计提醒我们：真实SDK析构可能阻塞甚至等待当前回调，本例无阻塞析构，不能直接套入设备后端。

发布只在进程内原子，不保证磁盘文件事务、断电恢复、签名/内容校验或跨进程一致性。上线清单应包含模型哈希、输入布局/量化格式、SDK版本及验证集版本；同目录rename也不能代替完整的持久化协议。`close` 只是停止新获取，拥有Registry的服务必须先join读者/管理线程再析构Registry。加载并发目前未限额，两个已发布代的约束不等于总内存上界。

## 工业故障与面试追问

下列是由合同构造的工程故障链，不是声称发生过的生产事故。

| 触发与信号 | 根因候选/最小诊断 | 修复和回归 |
| --- | --- | --- |
| 发布后旧请求崩溃 | 主机提交后释放旧模型；记录完成事件与版本销毁次序 | 回调持有租约至完成；注入慢请求并检查最后释放 |
| 慢候选覆盖新模型 | 构造完成时间被当作管理请求顺序；并发相同expected | 锁内检查revision；只有一个请求提交，另一个返回Stale |
| 连续发布后RSS上升 | 慢租约与无限候选；记录活跃代/加载中候选分别计数 | 退休代背压＋生产加载限额；验证拒绝后当前版本不变 |
| SDK析构卡住工作线程 | 最后引用在SDK回调释放且析构等待同线程 | 显式销毁执行器/完成协议，检查退出路径；本例未覆盖SDK |

追问：共享指针控制块安全是否代表对象安全？为什么一次请求只取一次快照？release/acquire发布保证了哪些写入可见？expected版本何时检查才有效？weak_ptr背压和内存总上限为何不同？设备提交返回后谁拥有模型？
