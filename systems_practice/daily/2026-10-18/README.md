# 2026-10-18 C++17 并发：有界请求队列的背压与关闭排空

## 工业场景

双相机机器人把已准备好的帧描述符送入CPU推理调度器：4个提交者、2个worker，每轮400个任务，队列容量分别为1和8。示例任务返回编号平方，每97个请求注入一次异常；真实接入时用拥有帧buffer的任务替换。目标是队列资源有界、超时保留所有权、已接收任务恰好执行一次、关闭后能排空并join。没有调用GPU/NPU，不能将主机任务完成等同于设备事件完成。本课只测并发合同，不宣称实时期限。

## 概念回顾

有界队列的核心不是给容器设置长度，而是定义谁在何时拥有请求。生产者准备任务后仍持有唯一句柄，只有在互斥锁保护下确认队列未关闭且存在空位，才把句柄移动进槽位；这一步是提交的线性化点。超时或关闭返回时，任务仍归调用者，可以取消或重试。容量约束只限制排队任务，不包括执行中的任务、提交者提前分配的帧和返回结果；工业服务还需要限制入口请求量，才能建立真正的内存上界。

条件变量负责等待状态变化，互斥锁负责状态与可见性。通知本身不储存许可，也不替代条件判断。生产者等待“关闭或有空位”，消费者等待“关闭或有数据”，两者必须在同一把锁下检查；等待操作原子地释放锁并进入等待，醒来重新取得锁并检查谓词，因而能容忍无效通知及其他线程抢先消费。使用单调时钟的绝对截止时间避免反复唤醒后重新计算相对超时，导致请求无限延期。

关闭协议与所有权转移紧密相连。关闭标志只能从开放变为关闭，必须同时唤醒等数据和等空位的线程。消费者仍取走已经接受的任务，仅在关闭且队列为空时退出；任务在锁外执行，避免慢请求阻塞所有提交。队列为空并不表示任务完成，析构必须等待worker结束，任务拥有的帧才能释放。这里用packaged_task把业务异常放入future，避免异常越过线程入口导致进程终止。队列先构造、worker后构造，逆序析构保证等待期间同步对象仍然活着；生产者则必须在队列销毁前退出。

## 知识图谱

| 连接 | 正确性条件 | 不要混淆 |
| --- | --- | --- |
| `Queue::push` → mutex → 移动句柄 | 状态检查与提交在同一临界区 | timeout不等于任务被取消执行过 |
| `space_/data_` → 谓词等待 | 同一mutex；close唤醒两侧 | notify不是计数信号量 |
| `pop` → 锁外任务 → future | 唯一消费；任务内部异常归结果 | 队列空不等于在途为零 |
| `Workers::~Workers` → close/join | 不在worker自身销毁，不与析构并发访问 | C++屏障不能证明GPU工作完成 |

语言层保证来自C++11以来的mutex/CV/future，工程代码按C++17编译。Linux常用futex作为阻塞基础，macOS实现不同；本课没有观测底层系统调用，不能声称每次wait都进入内核。

## 正确性验证

容量1/8分别400次提交，395个成功结果和5个指定异常；核验每个future对应编号。另测零容量/空任务拒绝、满队列立即超时、阻塞生产者被close唤醒、重复close、关闭后拒绝、已有任务排空、在途gate和第2个worker启动前故障回滚。生产者等待观察有2秒上限，提交有10秒上限；这是测试看门狗而非实时SLA。TSan通过只覆盖所运行调度，不是所有交错的形式证明。

## 性能分析

本课不测吞吐与P95，不把Sanitizer耗时当性能。每次排队有一次持锁提交/提取和相应通知；固定槽位消除队列扩容，任务/future自身仍可能分配。预计同时拥有的任务至少由`queue容量+worker数+提交者预备量`决定，帧buffer需另算。

上线测量应在提交前、提交成功、worker取走、任务结束各打时间戳：分别统计入口背压、排队、CPU执行与请求端到端。固定输入、线程数、容量，预热后采集独立请求分位数，另记拒绝率。容量增大会降低拒绝但可能恶化排队尾延迟；不保证提高吞吐。没有GPU kernel，因此今日GPU对照游标维持Hopper，下一次仍对照Ada；CUDA执行目标始终Thor SM110。

## 工程注意事项

API使用者必须保证queue活到生产者和worker退出之后，`close`可以并发调用，析构不可以与成员调用竞争。worker不能持有最后一个池所有者并销毁自己；任务不能同步等待同一饱和池里的新任务。任务内无限等待会让join无限等待，本例不是可强制取消系统。启动失败会关闭队列，这是本例明确的失败策略；生产实现若要重启，需新建对象，不重开旧队列。

## 工业故障与面试追问

1. 满队列关闭后进程卡死：生产者只等空位→close仅通知消费者→用等待线程栈和`waiting()`区分业务卡住/遗漏通知→close通知两侧；回归capacity=1阻塞提交。
2. 停服偶发访问已释放帧：队列空就销毁buffer→worker已pop但尚未完成→gate验证future仍未ready→先join再回收；代价是停服受最长任务约束。
3. 某请求异常导致后续全部丢失：异常穿过线程入口→terminate→核对future和错误日志→packaged_task隔离业务异常；同步设施失败仍是不可恢复错误，不吞掉。

面试追问：提交的线性化点在哪？为什么close唤醒两种CV？绝对截止时间解决什么问题？capacity=8能否保证只有8份帧内存？队列空怎样与完成区分？为什么不能在worker里析构本池？如何给关闭时间建立上界？
