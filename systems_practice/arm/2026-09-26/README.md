## 这个例子具体观察什么 ARM 机制

本例C++只负责构造跨函数调用；真正要学的是**AArch64参数寄存器、栈参数和被调用者保存寄存器**。run.sh直接打印caller的本次生成汇编，按下面顺序对照[归档文本](results/native-arm64.s)：

1. `sub sp, sp, #48`分配48字节栈帧；48为16的倍数。`stp x20, x19`保存caller将要改写的被调用者保存寄存器。
2. seed保留在x0，同时`mov x19, x0`为跨调用使用保留副本；常量2–8写入w1–w7，对应x1–x7中的参数。第九参数9由`str x8, [sp]`写到调用时栈顶。
3. `bl _combine`调用另一翻译单元。返回值在x0；之后`madd x0, x19, x20, x0`用跨调用保留的seed和19合成结果。
4. LDP恢复x19/x20和帧/返回地址寄存器，恢复SP后RET。若手写callee破坏需保存的寄存器，调用后的计算可能出错。

1000个seed的数值检查是正确性证据，寄存器/栈布局来自真实汇编。这里是Darwin的九个uint64参数观察；一般规则对照[AAPCS64寄存器与参数传递章节](https://github.com/ARM-software/abi-aa/blob/main/aapcs64/aapcs64.rst)，不能推广为Darwin与Linux全部ABI细节相同。

## 工程深入：把ABI当成内核接口合同

**工作目标**：替换热点为汇编、接入第三方算子或跨动态库调用时，能定位“单独测试正确，接入服务就错”的问题。ABI规定参数、返回值和哪些寄存器必须恢复；它不规定某个编译器一定使用x19保存某个C++变量。`caller`既是combine的调用者，也是main的被调用者，所以它既要让seed跨combine调用存活，也要在返回main前恢复自己改过的callee-saved寄存器。

从本机`caller`真实48字节栈帧画布局，以完成`sub sp,sp,#48`后的SP为基准：

| 地址区间 | 本次实际用途 |
| --- | --- |
| SP+0…7 | 第九个uint64参数，值9 |
| SP+8…15 | 本次未用于参数/保存的间隙，不推断业务值 |
| SP+16…23、+24…31 | 保存原x20、x19 |
| SP+32…39、+40…47 | 保存x29、x30 |

`mov x19,x0`保留seed；`mov w20,#19`写W并零扩展，所以x20成为64位19。`bl _combine`之后x0是加权和，`madd x0,x19,x20,x0`把seed×19再加上返回值。因此最终是`20*seed+284`，源码中1000个seed与这个独立表达式比较。注意真正跨调用保留的是seed和乘数，编译器把原C++的keep乘法推迟到返回后，这正说明不能把源码局部变量与固定寄存器机械一一对应。

### ABI成本怎样影响小内核

一个短计算如果每几个元素就跨函数调用，参数准备、分支、保存/恢复可能占比明显。不能数出几条STP/LDP就断言时间：缓存、流水线及调用次数都有关。可选手段包括扩大一次调用的工作量、在确有收益时内联、在合理范围内减少跨调用活值；代价分别是批处理延迟、代码体积和结构复杂性。当前noinline/禁LTO用于显露ABI，不是推荐生产中无条件禁内联；本课没有测调用开销，因而不推荐某个变体已经更快。

AAPCS64的寄存器保存和16字节栈对齐在2026-09-29重新核对[官方规范](https://github.com/ARM-software/abi-aa/blob/main/aapcs64/aapcs64.rst)§6.1与§6.4.5，页面为2025Q4；实际帧布局来自本机归档汇编。x18具有平台用途，不能作为“还剩一个通用临时寄存器”随意占用。当前只验证Darwin九个uint64参数，不含变参、结构体、浮点或跨语言异常边界。

### 接入第三方内核时的排障顺序

| 症状 | 最小辨别证据 | 修复和回归 |
| --- | --- | --- |
| 调用后无关变量变坏 | 比对调用前后需保存寄存器；确认函数声明与定义完全一致 | 修复callee保存协议或接口签名，复测跨调用活值 |
| 前八个整数参数正常，第九个错 | 比对调用时SP、栈参数地址、callee读取位置 | 依据目标ABI重新布局，不复制另一平台的变参规则 |
| 加入手写汇编后偶发崩溃/回溯混乱 | 核对SP恢复、保存返回地址与栈对齐；结合调用栈 | 保留清晰序言/尾声和目标工具链支持的展开信息 |

## 真实项目源码研读（2026-09-29补充）

把本课48字节栈帧与[Arm memcpy.S入口至ret](https://github.com/ARM-software/optimized-routines/blob/master/string/aarch64/memcpy.S)并排看：本课跨bl保存活值，上游例程是没有内部bl调用的叶函数。源码用x0保存返回的原目标指针，内部另有工作指针；它没有理由机械复制本课的保存/恢复序列。

阅读顺序是：列入口参数 → 标返回值 → 画每个值最后使用位置 → 找调用边界 → 核对哪些寄存器需要保存。这比“所有函数都保存x29/x30”更接近评审实际算子汇编的工作。若给该叶函数插入日志调用，原先可自由使用的临时寄存器可能跨调用失效，必须重新审计；不能只在中间加bl。这里只分析上游实现，未在本机替换libc或验证该实现的ABI移植。
