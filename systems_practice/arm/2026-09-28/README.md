上一节看了 X/W 寄存器；今天把寄存器中的地址连接到 ROCK 5B 的摄像头深度帧。教学输入为 UINT16 `[H,W]`，物理行长 `stride` 个元素。读取位置是 `base + 2*(row*stride+col)` 字节。行尾 padding 不是像素，不能把 H×W 当成连续缓冲区扫完。

选定教学板为 Radxa ROCK 5B/RK3588。[官方产品页](https://docs.radxa.com/en/rock5/rock5b/getting-started/introduction) 当日读取，CPU 为 Cortex-A76/A55；实际板端 OS、内核、核拓扑与 SDK 未采集，Mac 编译结果不代表这些核的性能。接板后先运行 `cat /etc/os-release`、`uname -a`、`lscpu -e`、`clang++ --version`，不预设核编号。

[Arm A64 ISA Guide 1.2 Issue02](https://documentation-service.arm.com/static/674d8b61c7fc0d1f211dc776?token=) 的 §15–18（印刷页30–37）解释传输宽度、零/符号扩展与地址模式。`LDRH` 从内存取16位零扩展；后索引先用旧地址，再推进基址。它本身不知道二维 Shape。C++ 指针下标按元素缩放，汇编偏移按字节，接口若以字节提供 stride，必须先验证可整除元素宽度。本例是独立教学代码，不声称改编某开源 kernel。

## 这个例子具体观察什么 ARM 机制

C++的二维stride并非ARM独有知识。本节要观察的是它如何落到A64的**半字加载、W/X宽度和后索引寻址**。执行run.sh后会直接打印本次生成的sum_rows汇编；程序PASS只证明求和正确，下面的指令才是ARM观察内容。

在[已归档汇编](results/stride-arm64.s)的sum_rows函数中，逐项对应源码：

| C++位置 | 本次A64指令 | 观察结论 |
| --- | --- | --- |
| 外层按stride个uint16前进行 | `lsl x10, x3, #1`、`add x0, x0, x10` | 元素行距乘2转换成字节行距 |
| 内层读取一个uint16 | `ldrh w13, [x11], #2` | 先取旧地址的16位无符号值，再将地址加2；结果零扩展到W，写W也清零X高32位 |
| uint64累加 | `add x8, x8, x13` | 加载宽度16位与累加宽度64位分开 |
| 内层计数与回跳 | `subs x12, x12, #1`、`b.ne` | SUBS更新条件标志，B.NE依据Z标志继续循环 |

观察现成36组数据中的有padding输入：内层只推进cols次，下一行从原行首加`2*stride`，因此不会累加poison padding。仅看最终和无法解释寻址方式，要同时沿x11的列指针和x0的行指针看。寄存器编号是该次编译器分配，重新编译可能变化；这些是Mac的A64指令观察，不能证明Cortex-A76的访存延迟。

## 工程深入：ROI接入与是否打包的工作决策

本日期是第03课的保留补充，不另推进课号。寻址推导见[顺序课03](../2026-09-24/README.md#工程深入从逻辑张量到可证明的地址范围)；这里重点解决另一个工作问题：把厂商张量/相机视图接进`sum_rows`前，怎样把字节跨度、ROI和容量变成可检查的接口合同。

### 字节视图到元素视图的逐步推导

假设SDK给出uint16图像、每行16字节，有效宽度6个元素，要取第1行第2列开始的高2、宽3区域。ROI起点的字节偏移是`1*16+2*2=20`，下一ROI行首仍增加16，而不是3*2。这里是示意地址，不是当前程序新增SDK支持。适配层必须先确认数据类型/端序、基址对象与对齐、缓冲区寿命，再确认字节stride可被2整除，才得到本接口的元素stride=8。不能对任意无类型内存强转指针后就认为完成了对象模型与SDK所有权检查。

若整个缓冲区容量是capacity_bytes，先检查ROI偏移不超过容量，再相减求可用容量，避免无符号下溢。非空ROI最高有效字节末端为`offset+(rows-1)*stride_bytes+cols*2`，各乘加都要先防溢出。当前`sum_rows`采用更严格的完整行容量合同，接入时要求ROI起点之后仍有`rows*stride`元素。对靠近缓冲区结尾的合法ROI，它可能拒绝——这是接口收窄，不能直接删除检查冒充支持。想改用最低跨度合同，需要单独实现和测试；本补充未偷偷改动原代码。

### 直接stride与紧凑packing如何选

直接逐行处理省去复制和额外分配，但每行有padding、跨行跳转；packing先把有效元素写入紧凑缓冲，可能让后续多个算子复用更方便。假设有K个后续遍历，每次stride路径耗时Ts、紧凑路径Tc，一次打包耗时Tp，那么粗略的盈亏条件是`Tp+K*Tc<K*Ts`。这只是串行时间预算，实际还要考虑打包与算子能否重叠、峰值内存、缓存污染和释放时机。本课没有测这些变量，不能预先推荐packing更快。

以H×W个uint16的逻辑payload为例，打包至少增加一次有效元素读取和一次写出，即逻辑4HW字节；不能说“忽略padding因此完全没有额外流量”。缓存/写分配使总线流量与这个逻辑量不完全相同。若只做一次小归约，复制开销可能难以摊薄；若很多下游核共同需要相同布局，则应把打包成本在整个流水线里计算，不重复隐藏到预处理之外。

### 三条实际排障路线

| 工作症状 | 辨别证据 | 修复与代价 |
| --- | --- | --- |
| 完整图正确，裁剪ROI最后几行错误 | 记录ROI偏移、原stride与剩余容量，不只看宽高 | 保留原物理行距；严格证明地址范围，适配层多几项检查 |
| 偶发读取旧帧或新帧混杂 | 查询SDK缓冲归属及何时允许复用，缩小引用寿命 | 租约覆盖处理或复制到自有存储；复制成本计入E2E |
| 打包后内核更快但总请求更慢 | 计时包含申请、复制、计算、释放，并记录K | 减少无收益打包或复用工作区；复用须有并发所有权协议 |

### 现成观察与验收边界

本课脚本的36组输入用poison padding检查布局，4种非法描述在读数据之前拒绝；这些证据不能替代ROI适配、SDK异步完成、并发所有权或packing性能测试。工作中可先按上述公式审查适配参数，再复用本课逻辑oracle。2026-09-29新增内容是基于本课源码的独立工程推导，没有声称读取某厂商SDK实现；接入具体设备时仍必须阅读其真实接口与同步合同。
