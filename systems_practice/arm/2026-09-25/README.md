## 这个例子具体观察什么 ARM 机制

**多累加器和指令级并行属于通用CPU原理**。本课的ARM部分是把C++循环映射到真实A64寄存器依赖和成对加载；没有测出A55/A76的流水线宽度或速度收益。run.sh现在直接打印serial和four的本次生成汇编。

在[已归档汇编](results/native-arm64.s)中：

- serial的`ldr x9, [x0], #8`加载一个64位元素；`add x8, x9, x8`每轮读写x8，形成跨迭代依赖。
- four的两条`ldp x14, x15, ...`每条读取两个64位值；四条ADD分别更新x8、x10、x11、x9。沿目的寄存器向上一轮追踪，就能看到四条分开的累加依赖链；x14/x15是重复使用的加载临时寄存器。
- 主循环每轮地址推进32字节，尾部仍用`ldr ... #8`；退出后用ADD合并四个累加器。1025个长度验证覆盖尾部和uint64回绕。

可先并排看两个函数，再用笔连出x8跨迭代的读写边；four中再分别连出四个目的寄存器。这是依赖图观察，不是“出现LDP就快两倍”或“四个ADD同时执行”的证明。下一步板端性能课才在指定核、相同输入与计时条件下测量。

## 工程深入：依赖链、资源上界与归因

**工作目标**：看到CPU归约循环很热时，判断增加独立累加器是否值得尝试。serial的递推式是`a(i+1)=a(i)+x(i)`；第i+1次ADD必须等待第i次产生a。four则维护4个递推，各自只依赖间隔4个输入的前一结果，末尾再合并。普通乱序执行可以调度已经就绪的独立指令，但不能凭空绕开真数据依赖。源码中的4个变量也不保证4条指令在同一周期执行。

可以先用**示意模型**组织假设：若某核ADD的依赖延迟为L周期、可持续吞吐为R次/周期，A条独立累加链仅就这个约束而言最多提供约`min(R,A/L)`次累加/周期。L和R必须来自具体核的资料或实测，本课没有填任何芯片数值。这个式子忽略加载、前端、分支与尾部，因此只是找瓶颈的工具，不是完整性能预测；当加载供给不足时再加链也不会增加吞吐。

本机A64的serial以x8作为反馈寄存器，four以x8/x10/x11/x9分别反馈。x14/x15只是当前加载的临时值，重复使用它们与累加器反馈不是同一个问题。four一次处理4个uint64，即32字节；两条LDP各取两个值。最后合并也有额外ADD和依赖，在N很小时可能比主循环省掉的成本更显著。

### 当前对照回答什么、还不能回答什么

本课证明两种实现对现有输入保持相同模2^64数值语义，并观察到不同A64依赖图。它**没有隔离ILP的纯收益**：four同时改变每轮处理元素数、分支频率、加载组合和寄存器使用。即使后续测出four更快，也只能先归于这一组实现变更，不能把整个比例写成“多累加器贡献”。想拆开原因，应安排同展开因子的一链与多链变体，并检查编译器是否重新结合整数运算；仅改源代码变量数不算隔离成功。这样的细分实验尚未在本课执行。

uint64模加法允许重新分组；若业务改成FP32归约，结合顺序会影响舍入，先确定误差合同再改算法。若改成signed整数并允许溢出，C++层本身就不再有本课的语义保证。HPC优化从数学/语言合同开始，不能只看生成指令漂亮。

### 生产问题的诊断与选择

| 症状 | 证据与候选原因 | 下一步及代价 |
| --- | --- | --- |
| 增加链数但没有变快 | 汇编里链确实分开，再看工作集/加载/分支；可能已碰其他资源上界 | 先建立公平基准，再扫描工作集；不要无限增加累加器 |
| 小N退化，大N改善 | 主循环入口、初始化、尾部、合并占比不同 | 依据实测选小N路径；分派和多版本维护也有成本 |
| 链数更多反而变慢 | 观察热点循环中新增栈访问与活值数量，区分spill与本来应有的访问 | 减少展开/链数，再验证；寄存器压力不是凭变量个数就能定量 |
| 浮点移植出现精度差异 | 固定输入，对比归约顺序与容限 | 明确数值目标，必要时用更高精度或稳定算法；代价另测 |
