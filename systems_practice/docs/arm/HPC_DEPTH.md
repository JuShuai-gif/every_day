# ARM：面向高性能计算与工作场景的深度要求

2026-09-29用户明确要求足够详细、有深度，并回补所有以往课程。这个要求优先于过去5–10分钟小课的篇幅限制。开头可速览，关键推导与工程分析必须在正文完整给出；每次仍聚焦一个核心问题，保留原前置顺序和唯一主作业，不把深度变成无关术语堆积。

## 每课应交付的八项内容

1. **工作负载合同**：具体岗位问题、shape/dtype/stride/规模、所有权、误差或整数语义、正常与失败输入。说明本课解决哪个阶段，哪些因素尚未纳入。
2. **机制推导**：从一个可手算的小输入开始，解释寄存器/地址/依赖/缓存/同步状态如何变化。给公式、单位与假设；区分架构保证、编译器选择、微架构与OS行为。
3. **代码与真实证据对应**：准确到函数和关键代码，摘录真实A64/NEON/ABI或硬件证据，解释操作数、依赖、地址、尾部。基础课不必硬塞手写汇编，不能只挂完整.s文件。
4. **性能问题与代价**：按本课适用性分析计算吞吐、依赖、加载存储、带宽、cache/TLB、分支或同步，不要求每课全讲。写清逻辑字节量与实际内存流量之别；不用整数ADD报告GFLOP/s，不从指令条数猜周期。
5. **可复现对照**：完整现成基线/候选、相同输入语义与容限，说明编译器是否自动向量化；隔离变量或明确混杂因素。解释输入分布、预热、样本单位、计时边界与P50/P95的意义。没有性能实验的基础课诚实标明，以兼容/正确性验收为主。
6. **排障与取舍**：至少两个不同故障链路，说明先采什么、哪条证据能区分候选原因、采取哪个修复、付出什么成本；给失败或无收益时的退路。
7. **迁移与上线验收**：给现成命令和检查表，核对目标拓扑/编译器/ABI/扩展、代表性shape、长期负载、热/频率、资源上界、E2E回归。不要把微基准提速直接等同业务收益；新平台验证必须单列。
8. **读后能力与追问**：明确读者应该能解释、复现、定位和选择什么；4–8个面试追问，仍不增加额外必做作业/自测。用证据界定能力，不承诺看完单课能处理所有生产故障。

## 平台与真实性

实际阅读Arm官方/编译器文档；源码课实际阅读成熟项目具体函数，记录版本、路径与原场景。引用与独立推导分清。macOS日志证明本机结果，不能替代Cortex/Neoverse板端的吞吐、PMU或温控验收；Linux命令在Mac未运行必须标出。硬件计数器先查可用事件与计量域，不把不可用当零；事件复用、权限和采样扰动要解释。

正常C++优化、NEON与可选扩展渐进推进。GPU内容仍固定Thor SM110，但SM编号不用于描述ARM CPU。ARM日期目录继续不生成JSON；来源和验证写README，保留旧日志，新增结果另存文本。历史课深化不移动学习游标、不重写原运行日期、不覆盖用户批注。

## 历史课回补如何验收

逐课定位当前代码与真实日志，再增补该课专属机制推导、至少两个工作故障、优化边界、迁移检查与追问。9月28日stride补充课用接口适配/ROI/packing决策深化，与第03课寻址推导区分。缺少的实测条件明确保留待验，不用文档篇幅冒充已完成实验。目录中的本次复验日志标明日期；编译/运行过与仅审阅过分别记录。
