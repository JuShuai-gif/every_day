# 后续课程：从实际源码到工程验收

2026-09-29用户确认：后续规划采用与[本轮源码研读](arm/SOURCE_STUDIES.md)相同的标准。适用于主练习、每日量化、ARM、C++17、OS和论文六个栏目；ARM另须满足[高性能计算深度要求](arm/HPC_DEPTH.md)。本文件定义规划和生成门槛，不是新增课程已读、已实现或已验证的记录。

## 每个选题在开课前要补齐什么

1. **真实工作问题**：明确输入合同、所在阶段、正常/失败条件、读完能处理的具体问题。先定问题，再找资料。
2. **实际检索与阅读**：用Google、知乎原作者/工程博客找有代码和测量过程的案例，追到GitHub具体版本、文件、函数和调用链，再用官方规范核查关键结论。记录真实查询/尝试URL、阅读范围和失败；某渠道无合适材料就如实说明，不硬凑引用。
3. **批判性采用**：写清原场景、保留机制、原始/改编/启发关系、许可及简化边界。明确哪些输入、架构、库版本或测量方式使博客结论不成立。一个链接列表不算完成源码研究。
4. **机制与证据闭环**：用可手算输入/状态图连接核心代码、指令或系统行为；给现成基线、候选与边界/反例。至少展开两个本课特有故障链，说明如何区分原因、修复代价和回归条件；提供4–8个追问。论文栏目将其放在复现分析中，避免凭空编造作者故障。
5. **公平评价与迁移**：给工具命令、定位对象、计量域、样本单位、输入分布和混杂因素。分析无收益/退化情形与上线验收；无性能实验的基础课报告功能/合同证据，不强行测速度。缺设备单列未验证，不能用模型、CPU或Mac替代目标硬件验收。

每天仍只有一个20–30分钟主编码任务和一个无答案自测；附加栏目的代码为已写好示例。短阅读时长只作速览，不限制必要推导。主课的450–700字概念回顾和十二标题保持，深度放入已有工程/验证/性能章节或相邻专题文档，不靠改标题和增加作业量解决。

## 规划如何变成可核查的交付

`research_plan`是待执行计划。每天先读当节计划，再真正获取/阅读来源，最后在该期README/已有来源与验证记录填写证据。不得把候选仓库、拟查函数或搜索词写成已读源码，不批量提前设置完成状态。

检索失败、版本无法固定、依赖缺失、设备缺失分别记原因与待补动作，按各栏目已有backlog规则处理；不为凑日期伪造进度，也不改变现有独立轮换与同日去重规则。ARM日期目录仍只在README及文本日志记录，不恢复JSON。量化继续要求实际拉取、原生API/CLI和独立校准/训练/评估；论文继续区分作者报告、独立示例与完整复现。

CUDA执行目标始终Thor SM110；其他GPU架构仅比较原理。C++17保留独立栏目。ARM基础源码观察不能替代HPC性能实测；xv6观察不能替代Linux/板端证据。候选来源在开课前核实仓库位置、版本、许可证、符号与工具链。

下面的项目名称/代码区域是检索线索，**本次没有预读这些未来实现，也不保证当前路径或API仍存在**。开课时必须找到真实文件/符号；不存在就更换并说明原因。已读历史资料可承接，但要注明复用范围与当课新增研究。逐课查询词、候选和验收目标同时写入[课程表](../arm/curriculum.json)。

## 其他栏目如何落实

- **主练习12方向**：轮到主题时用当期工业合同构造查询与源码阅读目标；GPU同时完成基线/优化、ncu定位采集、真实ISA或完整待执行命令及架构对照，不能只增加博客段落。
- **每日量化**：以独立游标的方法原仓库为主；博客辅助讲算法选择和失败，不能替代实际训练更新、原生用法、真实打包、误差/存储及公平性能边界。
- **独立C++17**：未来每课的研究计划从既有两个机制出发，追语言保证到库实现及业务失败路径。安全构造边界例子，不能执行UB来“证明”语言规则。
- **独立OS**：从既有edge_problem和source_candidates追资源/同步调用链，再对照Linux接口；不把xv6教学简化当作生产行为。至少两条可辨别故障与目标平台证据。
- **两篇论文**：先读原论文方法/实验/局限与作者实现；博客解释与复现笔记要能回溯原始证据。无作者代码或未跑完整实验时保留边界，不能靠独立小例子写“复现成功”。

本次只更新规划、模板和要求；不重排既有课程、不推进任何游标。下一节仍是ARM08、C++17 02、OS03，其他栏目沿各自索引继续。
