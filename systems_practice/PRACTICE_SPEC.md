## 当前 Mac 环境与 GPU / NPU / ARM 验证边界

- 当前开发机器为 Mac，没有可用于 CUDA 的 NVIDIA GPU。将本机作为资料生成、CPU 参考实现和可行静态检查环境；GPU 执行以兼容的 Linux NVIDIA GPU / Jetson 目标设备为准。
- 硬件缺失只限制本机验证范围，不改变主题轮换或内容深度。不得跳过 CUDA、TensorRT、PTX / CUTLASS、GPU 访存优化、GPU 体系结构，也不得将这些主题替换成纯 CPU 或 Metal 练习。
- 每个涉及 GPU 的练习仍必须包含完整目标代码、构建配置、输入生成或最小数据说明、依赖与兼容性要求、目标设备编译运行命令、正确性标准、性能分析命令和待记录指标。保持一个核心概念、一个编码练习、一个自测问题，不额外增加练习。
- README 的编译运行与实际运行结果应明确区分“Mac 本机可验证部分”和“Linux NVIDIA GPU / Jetson 目标设备待验证部分”。可移植 CPU 参考或数据检查属于同一练习的辅助验证，不能替代 GPU 实现与验收。
- 没有目标设备时明确标记 GPU 编译、执行、精度和性能中哪些未验证，并说明缺少的工具或数据。不得用 CPU 性能、理论推算或模拟结果冒充 GPU 实测，不得声称 Mac 上运行容器即可获得 CUDA GPU 能力。

- RK3588 NPU / RKNN 主题必须保留 ONNX → RKNN 模型转换与 RK3588 板端推理实现。缺少工具链或板卡时，仍生成完整转换脚本、C++ Runtime 代码、构建配置、可生成的最小 ONNX/输入、校准样本说明和板端命令；不能以 CPU 推理替代 NPU 实现，也不能编造已转换出的 `.rknn` 文件。
- ARM SIMD / NEON 是独立的通用 ARM CPU 优化方向，优先利用当前 Apple Silicon Mac 的 arm64 环境实际编译、运行、查看生成指令和测量性能，无需绑定 RK3588。提供标量参考与真实 NEON intrinsics 实现；仅在该练习明确涉及跨平台移植时，再分别验证 RK3588 或其他 ARM 设备。根据本机或所选目标 CPU 和工具链检查指令扩展，保留尾部处理与必要的标量回退，不默认支持 SVE/SVE2 或所有可选扩展；不同微架构的性能结论不能直接互相外推。
- 对 RKNN 分开记录模型转换、CPU/ONNX 参考、板端 Runtime 推理、精度和性能验证状态；区分 CPU 预处理/后处理时间、主机 Runtime 调用时间、工具实际提供的 NPU 设备时间以及端到端延迟。主机 API 耗时不得直接标成 NPU 内核耗时。

## 场景与内容

优先结合 RK3588 的 ONNX → RKNN → NPU 部署、Apple Silicon Mac 上的 ARM CPU 张量计算/量化与 NEON 优化、Jetson Thor 或同类边缘 GPU、VLA/视觉编码器/机器人感知控制、TensorRT、FP16/FP8/FP4/INT8、小 Batch/Small-M GEMM/低延迟、双相机/动作 Chunk/实时控制、Kernel 优化与融合、C++ 推理服务/生产者消费者、CPU/GPU 异步调度、容器/交叉编译/运行时排障。

每次练习 20～30 分钟，严格只有一个简洁概念回顾、一个可操作工程编码练习、一个分析性自测问题（不立即给答案）。配套说明和验证章节不得引入其他练习。

必须明确真实背景、输入输出、代表性 Tensor Shape/Batch/规模、时延/吞吐/显存/内存/功耗或并发安全约束、编译运行命令、正确性标准、性能验收方法、记录指标、常见故障与边界、部署取舍。只引用已核实资料，硬件兼容性不凭空猜测。

### 选题深度与开源项目来源

- 例子应有工程深度，优先从知名、成熟开源项目中提炼一个小模块、关键实现或知识点，也可围绕一个有实际价值的底层机制自行构造最小示例。控制范围，使练习仍可在 20～30 分钟内完成。
- 选题必须落到一个具体设计问题：解释它解决什么真实问题、依赖哪些正确性条件、为什么采用这种实现，以及性能或资源方面的取舍。在同一个编码练习中，用可操作的改动和边界测试或测量验证这个设计点；避免停留在 API 调用演示或简单算术示例。
- 使用开源项目作为来源时，先阅读并核实相关源码，在 README 现有章节中给出仓库链接、版本或 commit、具体文件与关键函数，说明原项目场景、练习保留的机制和省略的复杂性。明确区分原始实现、改编和受其启发的独立实现，不凭印象归因，也不要求下载或构建整个大型项目。

### RK3588 NPU / RKNN 与独立 ARM SIMD 方向的选题范围

- **RK3588 NPU / RKNN**：围绕 ONNX 算子与 Shape 支持、模型转换与图优化、预处理一致性、INT8 校准与量化误差定位、输入输出布局/类型/量化参数查询、C++ RKNN Runtime 的资源生命周期、stride 与缓冲区约束、内存绑定/减少复制、多核调度及 CPU–NPU 流水线选一个点深入。具体 API、算子支持、内存一致性和核调度能力以选定 SDK/驱动版本的官方文档与源码为准，不能把候选选题当作所有版本都支持的能力。
- **ARM SIMD / NEON**：以 ggml、ncnn 的 ARM CPU 实现作为优先源码来源，围绕 `arm_neon.h` intrinsics 与 AArch64 生成指令，练习向量加载/存储、交错与重排、扩宽累加、饱和/舍入/窄化、归约、尾部与步长处理、浮点误差及可选 dot-product 扩展。优先从量化块与点积、反量化和累加、小矩阵/矩阵向量计算、张量 stride、packing、归约等机制中选一个点；图像预处理/后处理只是可选场景。每次先核实实际源码，再提炼可在 Mac 本机运行的最小实现，比较标量参考与 SIMD 结果、检查生成指令并分析访存或计算瓶颈。
- NPU 侧优先从 Rockchip 官方 RKNN-Toolkit2、RKNN Model Zoo、RKNPU2 示例提炼问题；SIMD 侧优先从 ggml、ncnn 借鉴，按相关性补充 OpenCV、Arm Compute Library 等成熟项目；仅选 CPU/ARM 路径时，不把 Metal/GPU 后端性能记成 NEON 性能。每次仍需实际阅读并标明来源版本/文件/函数，不能仅挂项目名称。
- 转换工具、板端 Runtime 与内核 NPU 驱动分别记录版本，并核实相互兼容性。区分 RKNN-Toolkit2（转换等工具）、RKNN-Toolkit-Lite2（板端 Python 接口）和 RKNN Runtime（板端 C/C++ 接口）。不默认 Mac 可原生运行 RKNN 转换工具，也不默认 PC 生成模型已经在板端通过精度测试。
- 每次只围绕一个机制设置一个编码练习；NPU 和 SIMD 独立选题，只有确实有帮助时才共享部署背景，不把完整模型转换、量化、流水线和 SIMD 优化全部塞进同一天。

## 文件与 README

每次至少包含 README.md、src/ 下真实代码、CMakeLists.txt/Makefile/build.sh 之一和 run.sh。CUDA 用 .cu，C++ 用 .cpp/.hpp，TensorRT 可用 .cpp/.py/.sh，RKNN 用转换 .py 和板端 .cpp/.hpp，ARM SIMD 用含真实 intrinsics 的 .cpp/.hpp，PTX 用 .cu/.ptx，部署可用 Dockerfile/CMake/Shell/配置。涉及 Roofline、访存、流水线、时间线或性能比较时可以额外生成无在线依赖、可直接打开的 index.html；不强制生成。

README 一级标题是日期与主题，必须有以下二级标题，顺序一致：工业场景；概念回顾（中文 300～500 字，只讲一个核心概念）；编码练习；文件说明；编译与运行；正确性验证；性能分析；实际运行结果；工程注意事项；自测问题（只有一个，不附答案）。

## 代码与验证

- 代码示例必须配有简短的中文注释，说明关键函数和主要步骤在做什么、为什么这样做；重点解释 Shape/内存布局、资源生命周期、同步与计时边界、错误处理等容易误解的地方。构建与运行脚本的关键步骤也应有中文注释，避免仅用英文注释或逐行复述语法。
- 代码可直接编译运行，不用伪代码；C++ 默认 C++17；明确错误检查，所有 CUDA API 及返回状态的 RKNN API 检查返回值，清理阶段也检查并报告错误。
